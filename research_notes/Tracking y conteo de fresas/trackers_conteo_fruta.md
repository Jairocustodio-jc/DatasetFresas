# Multi-object tracking + YOLO for fruit counting from a moving camera (strawberry first; apple, tomato, citrus, blueberry, grape)

Context for these notes: a strawberry MONITORING robot (Raspberry Pi 5, CPU) that must count fruits per ripeness class per plant/row, using either a single-stage YOLO (5 ripeness classes) or a two-stage pipeline (class-agnostic YOLO detector + crop classifier).

Access caveat for the report writer: in this session most publisher hosts (mdpi.com, arxiv.org, ncbi/PMC, sciencedirect, frontiersin, springer, thecvf, researchgate, semanticscholar, ar5iv) were blocked at the network level, so full texts could NOT be read directly. Figures below marked **[abstract/secondary]** come from abstracts or from search-engine summaries of the full text; figures marked **[primary, read]** come from pages that were fetched and read (Ultralytics source code and tracker YAMLs, GitHub READMEs). Treat exact decimals from [abstract/secondary] items as "verify against the PDF".

## KQ1. Which papers (2020–2026) do strawberry counting with YOLO + tracker? Dataset, tracker, counting accuracy, per-ripeness-class results

### Takeaway
The most directly relevant work is Karki et al., *Agriculture* 2025 (optimized YOLOv8s + "class-aware" ByteTrack + virtual counting line): overall R² = 0.914, MAPE = 9.52 % vs manual, ripe class R² = 0.950; the per-class values 0.752 (semi-ripe) and 0.910 (unripe) quoted in the assignment were NOT found in any accessible abstract or summary and must be checked in the full PDF. Three other strawberry tracking-counting works exist (YOLOv7-pruned + "information-based" tracker, 2024 arXiv; YOLOv5s/ViT + StrongSORT "DynCount", ASABE 2023; BF-LQE-YOLOv11 + modified BoT-SORT with counting zone, SSRN 2025 preprint, 97.84 % counting accuracy, MOTA 83.7 %), plus a plant-factory monitoring robot (Ren et al. 2023) that counts ripe fruit from keyframes.

### Cited Findings
- Primary source of the "YOLOv8s + class-aware ByteTrack" strawberry work: Karki et al., "Real-Time Strawberry Ripeness Classification and Counting: An Optimized YOLOv8s Framework with Class-Aware Multi-Object Tracking", *Agriculture* 2025, 15(18), 1906, DOI 10.3390/agriculture15181906 — [MDPI DOI](https://doi.org/10.3390/agriculture15181906); mirror listing at [EconPapers](https://econpapers.repec.org/article/gamjagris/v_3a15_3ay_3a2025_3ai_3a18_3ap_3a1906-_3ad_3a1745156.htm) and [ResearchGate](https://www.researchgate.net/publication/395445574_Real-Time_Strawberry_Ripeness_Classification_and_Counting_An_Optimized_YOLOv8s_Framework_with_Class-Aware_Multi-Object_Tracking). **[abstract/secondary]**
- Reported results (abstract): optimized YOLOv8s reaches 92.5 % mAP@0.5 with 27.9 % fewer parameters; on validation video, counts vs ground truth R² = 0.914, MAPE = 9.52 %; counting most accurate for ripe fruit, R² = 0.950 — [MDPI DOI](https://doi.org/10.3390/agriculture15181906). **[abstract/secondary]**
- Counting mechanism (as summarised from the full text by search): the authors argue that counting every detection across a video over-counts when the camera moves along greenhouse rows, so they use a virtual line-crossing trigger; the counting zone is a vertical ROI at the centre of the 1920×1080 frame and a fruit is counted when its bounding-box centroid enters the zone; tracking is done with ByteTrack "according to the ripeness class across frames"; one summary says they "implemented modifications to its Kalman filter so the system can separate ripeness stages" — [MDPI DOI](https://doi.org/10.3390/agriculture15181906). **[secondary; exact ByteTrack thresholds/track_buffer and the semi-ripe / unripe R² values were not retrievable]**
- Strawberry (Florida; flowers, immature, mature): Liu et al., "Strawberry detection and counting based on YOLOv7 pruning and information based tracking algorithm" (arXiv 2407.12614, 2024). Pruning YOLOv7 detection heads: Pruning-YOLOv7-tiny (head 3) fastest at 163.9 FPS; Pruning-YOLOv7-tiny (heads 2+3) best accuracy 89.1 %. The "information-based tracking algorithm" (IBTA) drops the Kalman filter and uses moving direction, velocity and spatial position (camera speed/direction known), and improved MOTA and MOTP by 12.3 % and 6.0 % over a centroid tracker (CTA); IDF1, IDR, IDP, MT, IDs also favoured IBTA — [arXiv abs](https://arxiv.org/abs/2407.12614), [arXiv PDF](https://arxiv.org/pdf/2407.12614). **[abstract/secondary; no end-to-end count-error vs manual found in the abstract]**
- Strawberry, StrongSORT: "A Dynamic Object Counting Method for Strawberry Fruits using Vision Transformer Networks and Kalman Filter Tracking" (ASABE 2023): improved YOLOv5s detects per frame, StrongSORT (Kalman + Hungarian) tracks IDs, a "DynCount" module maps track IDs to a running count — [ASABE abstract](https://elibrary.asabe.org/abstract.asp?JID=5&AID=54240&CID=oma2023&T=1). **[abstract; no numeric count error visible in the abstract snippet]**
- Earlier strawberry+SORT: "Counting of Strawberries and Flowers in Fields using YOLOv4 and SORT" (ASABE 2022) — [ASABE](https://elibrary.asabe.org/azdez.asp?JID=5&AID=53701&CID=hou2022&T=2). **[title only; numbers not retrieved]**
- Strawberry, BoT-SORT (preprint): Huai et al., "Strawberry Ripeness Detection and Fruit Counting in Densely Occluded Environments Based on BF-LQE-YOLOv11 and BoT-SORT" (SSRN 7565041, 2025): improved YOLOv11 (feature-fusion redesign + Localization Quality Estimation for small/partly visible berries) + BoT-SORT modified with "Observation Center Recovery" and "Observation Re-Update" to counter Kalman drift during long occlusions; a virtual counting zone deduplicates counts at trajectory level; mAP@0.5:0.95 0.833, MOTA 83.7 %, counting accuracy 97.84 %; a greenhouse strawberry video dataset covering multiple ripening stages, dense occlusion and complex backgrounds was built — [SSRN](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=7565041). **[abstract; preprint, not peer-reviewed]**
- Strawberry monitoring robot in a plant factory: Ren et al., "Mobile robotics platform for strawberry temporal–spatial yield monitoring within precision indoor farming systems", *Frontiers in Plant Science* 2023: YOLOv5 detects ripe fruit on each tier; yield = total ripe fruit detected; ground truth by manual counting; the platform moved at 0.3 m/s along the aisle; keyframe spacing was modelled as a function of frame rate, travel speed, camera intrinsics and fruit distance, with little change in the extracted-frame interval error when frame rate r > 15 and v = 0.2/0.3/0.4 m/s — [PMC10167025](https://pmc.ncbi.nlm.nih.gov/articles/PMC10167025/). **[secondary]**
- Strawberry ripeness detection with BoT-SORT-ready detectors: STRAW-YOLO (fruit + key points) — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0168169924012444) — detection only, no tracking numbers. **[title/abstract]**

### Inferences
- Across the strawberry literature the recurring counting primitive is a centre-of-frame vertical counting zone/line plus a track ID, not "number of unique IDs". Both Karki 2025 (ByteTrack) and Huai 2025 (BoT-SORT) use a zone; the Pi-5 robot should do the same.
- Per-class counting is markedly worse for intermediate ripeness in the only paper that reports it (ripe R² 0.950 vs overall 0.914 ⇒ the non-ripe classes must be below 0.914); this is consistent with class flicker between adjacent ripeness stages inflating/deflating per-class counts.
- A strawberry MOTA of ~84 % (Huai) and tomato MOTA 0.954 (Zheng, KQ-tomato below) are the realistic tracking ceilings in greenhouses; counting accuracy can still be high (>95 %) when a zone + track-level deduplication is used.

### Gaps
- The exact per-class figures R² = 0.752 (semi-ripe) and 0.910 (unripe), ByteTrack parameter values, dataset size, camera and fps for Karki et al. 2025 could not be verified (mdpi.com, researchgate, econpapers blocked). Only ripe = 0.950 and overall 0.914 / MAPE 9.52 % are confirmed from the abstract.
- No strawberry paper found that reports ID switches or HOTA numerically in an accessible abstract.
- No strawberry paper found that counts per plant (only per row/video); Ren et al. do per-plant/per-tier monitoring but via keyframes rather than MOT.

## KQ2. Apple/orchard counting with tracking (MinneApple; Häni/Roy/Isler; Gao; Villacrés; others): accuracy and double-counting handling

### Takeaway
Apple work shows (a) naive tracking-by-detection counts carry ~20 % error (Villacrés 2023: DeepSORT 20.07 % with YOLOv5), (b) improved association or motion-aware tracking brings counting accuracy to ~91–94 % (Gao 2022 trunk-tracking 91.49 %; GMC-DeepSORT UAV 93.5 %; AD-YOLO+MR-SORT R² 0.98), and (c) 3D/SfM or odometry association is the strongest remedy against double counting after occlusion (Liu 2018: mean error 17.1 % → −0.2 % for oranges after 3D correction; Matos CVPRW 2024 for low frame rates).

- Apple stereo MOT (TUHH thesis/publication): OC-SORT with optical flow best on validation set, HOTA 0.59, MOTA 0.52, IDF1 0.67, vs ByteTrack — [TORE](https://tore.tuhh.de/entities/publication/f5ac606c-42b1-4eca-8a4d-afb6c5bfb795). **[secondary]**

- Other apple tracking-count works surfaced (not read): YOLOv7 + multi-head attention + ByteTrack outperformed DeepSORT in counting (Computers 2024, 13(3):83) — [MDPI DOI](https://doi.org/10.3390/computers13030083); improved YOLOv11 + DeepSORT yield model (Agriculture 2025, 15(7):765) — [MDPI DOI](https://doi.org/10.3390/agriculture15070765); YOLOv7-Tiny-PDE tracking count (Agriculture 2025, 15(5):483) — [MDPI DOI](https://doi.org/10.3390/agriculture15050483). **[titles/abstract snippets only]**

### Inferences
- The gap between "tracking metric" and "count accuracy" is systematic: MOTA/HOTA of 0.5–0.6 can still yield MAPE < 10 % because FP and FN compensate (explicitly warned by the 2026 edge paper). For a monitoring robot, event-level precision/recall of counted fruits (not just total error) should be the validation metric.
- Odometry/3D association (trunk tracking, SfM, IMU odometry) is what moves apple counting from ~80 % to >90 %; a Pi-5 robot with wheel odometry can emulate this cheaply by predicting horizontal pixel displacement from robot speed (as Gao's trunk tracking and Liu's IBTA do).

## KQ3. ByteTrack vs BoT-SORT vs DeepSORT (and OC-SORT/StrongSORT) in agriculture: comparisons with numbers; lightest for CPU

### Takeaway
In fruit-specific comparisons, ByteTrack and OC-SORT are usually best or tied among lightweight trackers (blueberry: ByteTrack 72.49 % vs OC-SORT 72.08 % mean counting accuracy, StrongSORT far worse at 24–59 %; tomato: ByteTrack > Motpy, FairMOT), BoT-SORT improves tracking metrics over ByteTrack by a few points under camera motion (apple: +4 % MOTA, +3 % IDF1, +6 % HOTA), and DeepSORT/StrongSORT appearance models add large CPU cost without clear counting benefit on look-alike fruit. ByteTrack (motion-only, no appearance network, no GMC) is the lightest; BoT-SORT without ReID adds only the optical-flow GMC cost.

### Cited Findings
- Blueberry (STF-YOLO + ByteTrack, *Frontiers in Plant Science* 2025, 10.3389/fpls.2025.1682024): mAP50 79.7 %; mean per-class counting accuracy (mPc) 72.49 % (blue 78.84 %, purple 74.38 %, green 64.24 %); per video: ByteTrack 69.07 / 74.94 / 73.45; OC-SORT 67.73 / 77.75 / 70.76; StrongSORT 59.32 / 24.30 / 37.32; averages ByteTrack 72.49, OC-SORT 72.08; green class fell to 60.92 % in one video (low contrast); authors say severe occlusion still causes missed detections and counting errors — [PMC12695768](https://pmc.ncbi.nlm.nih.gov/articles/PMC12695768), [Frontiers](https://www.frontiersin.org/journals/plant-science/articles/10.3389/fpls.2025.1682024/full), [PubMed](https://pubmed.ncbi.nlm.nih.gov/41393872/). **[secondary summary of full text; note the text's "ByteTrack best on all" claim conflicts with OC-SORT winning Video 2]**

### Inferences
- For a Pi-5 CPU with ~5–8 FPS detection, the tracker is negligible cost for ByteTrack and small for BoT-SORT-without-ReID; the real cost driver is detector FPS, which also governs how far fruit move between frames (see KQ6/7). ReID (DeepSORT/StrongSORT/BoT-SORT with_reid) is both the most expensive and, in blueberry/citrus evidence, the least helpful for look-alike fruit.
- BoT-SORT's GMC (sparse optical flow) is the one feature that directly addresses a moving robot camera; evidence (apple 2026, UAV GMC-DeepSORT) says it helps tracking metrics a few points. Worth A/B testing on the Pi; if too slow, emulate GMC with odometry.

### Gaps
- No paper measures ByteTrack vs BoT-SORT latency on a Raspberry Pi; all CPU numbers are modelled or from laptops/GPUs.
- No fruit paper directly compares ByteTrack, BoT-SORT, OC-SORT, StrongSORT and DeepSORT all on the same data with counting error.

## KQ4. Class-aware vs class-agnostic tracking when fruit class flickers between frames

### Takeaway
Ultralytics' ByteTrack/BoT-SORT association is class-agnostic (IoU/motion only) and each matched track simply overwrites its `cls` with the latest detection's class with no voting; the one strawberry paper that is "class-aware" (Karki 2025) counts per class with ByteTrack and shows per-class R² degrading away from the ripe class, while works that aggregate labels over a track (cherry-tomato: most-frequent ripeness value across detections of the same bunch, 90.84 % ripeness accuracy; apple 2026: majority vote over frames) explicitly do so to suppress frame-level inconsistencies. No paper was found that quantifies class-split tracks vs agnostic+vote on the same data.

### Cited Findings
- Ultralytics ByteTrack code (`ultralytics/trackers/byte_tracker.py`): association costs are `matching.iou_distance(tracks, detections)` optionally fused with score and never check class, so a detection can match a track of a different class; on a match the track takes the detection's class (`self.cls = new_track.cls`) in `update()` and `re_activate()`, with no history or voting — [raw source](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/trackers/byte_tracker.py). **[primary, read]**
- Ultralytics `track.py`: no class-based filtering anywhere; detections go to the tracker as a whole array; track IDs are written back by indexing the original detections (`idx = tracks[:, -1]`), so the class exposed per frame is the per-frame detection's class — [raw source](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/trackers/track.py). **[primary, read]**
- Ultralytics docs: tracker parameters are global; a maintainer said it is "not possible to set tracker parameters individually per ID"; the `classes` argument restricts which classes are tracked at all — [GitHub discussion](https://github.com/orgs/ultralytics/discussions/2687), [discussion #10074](https://github.com/orgs/ultralytics/discussions/10074). **[secondary]**
- Common per-class counting pattern (set of IDs per class) double-counts an ID whose class flips between frames, since the ID lands in both classes' sets — [search summary of Ultralytics community material, e.g. Academy](https://academy.ultralytics.com/courses/yolo-in-production/tracking-with-bytetrack-and-botsort). **[secondary/inference by search tool]**
- Karki 2025 strawberry: ByteTrack "according to the ripeness class across frames" (class-aware); ripe-class counting R² 0.950 vs overall 0.914 — [MDPI DOI](https://doi.org/10.3390/agriculture15181906). **[abstract]**
- Qi et al. 2024, cherry tomatoes (*Measurement*, S0263224124000010): NanoDet detector; bunch ripeness = ratio of ripe to unripe fruit; "to limit shading-related errors, the ripeness value with the highest frequency is selected as the estimate when multiple detections of the same bunch are detected"; five ripeness levels combined with counts; 92.79 % counting accuracy, 90.84 % ripeness-level accuracy, 15 FPS — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0263224124000010). **[abstract]**
- Apple 2026 scanning-conditions study: each tracked fruit assigned to the stretch it appears in most often; "the final stretch label is determined through a majority-vote strategy, reducing the influence of occasional tracking inconsistencies" — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0168169926009282). **[secondary]** (Spatial label, but same mechanism as per-track class voting.)
- Tomato ripeness + ByteTrack GitHub project (YOLO26, conveyor): "ripeness voting → up to 3 well-framed views per tomato, averaged", class-agnostic evaluation stage; self-reported 95–99 % counting accuracy on conveyor — [GitHub ParsaVictor](https://github.com/ParsaVictor/tomato-ripeness-detection). **[non-peer-reviewed README]**
- Blueberry per-class counting accuracy drops for the intermediate/low-contrast class (green 64.24 %, blue 78.84 %) — [PMC12695768](https://pmc.ncbi.nlm.nih.gov/articles/PMC12695768). **[secondary]**

### Inferences
- Because Ultralytics' trackers are already class-agnostic in association, "class-aware tracking" in Ultralytics practice means only (a) filtering by `classes=` (one tracker run per class, risking split tracks when a fruit's class flips) or (b) reading the per-frame `cls` of each ID. Option (b) with per-frame class is exactly the flicker-prone pattern; a per-track class histogram (majority vote or confidence-weighted vote, finalised when the track crosses the counting line or is removed) is the approach the cherry-tomato and apple papers use and fits the two-stage pipeline (detector-agnostic track → classifier vote on N best crops).
- For the two-stage pipeline, voting also lets you classify only a few crops per track (e.g. the 3 most centred/largest, as in the tomato project), cutting classifier cost on the Pi.

### Gaps
- No peer-reviewed study found that quantifies the counting error difference between per-class tracking and class-agnostic tracking + label voting for fruit.
- How Karki 2025 implements "class-aware" ByteTrack (separate tracker per class vs class-gated matching vs modified Kalman state) could not be verified.

## KQ5. Ultralytics `model.track()` (ByteTrack / BoT-SORT built in): parameters, persist mode, known limitations

### Takeaway
Ultralytics ships `bytetrack.yaml` and `botsort.yaml` with identical shared defaults (track_high_thresh 0.25, track_low_thresh 0.1, new_track_thresh 0.25, track_buffer 30, match_thresh 0.8, fuse_score True); BoT-SORT adds gmc_method sparseOptFlow, proximity_thresh 0.5, appearance_thresh 0.8, with_reid False; `track_buffer` is used directly as a frame count (not scaled by fps) in the current code; `persist=True` keeps tracker state across successive `track()` calls on consecutive frames; the current default tracker in recent releases is TrackTrack, with OC-SORT, Deep OC-SORT and FastTracker also available.

### Cited Findings
- `botsort.yaml` defaults (read verbatim): tracker_type botsort; track_high_thresh 0.25 ("raise for cleaner tracks, lower to keep more"); track_low_thresh 0.1 ("balances recovery vs drift"); new_track_thresh 0.25 ("higher reduces false tracks"); track_buffer 30 ("frames to keep lost tracks alive; higher handles occlusion, increases ID switches risk"); match_thresh 0.8 ("tune with detector quality"); fuse_score True; gmc_method sparseOptFlow (options sparseOptFlow|orb|sift|ecc|none, "helps moving camera scenes"); proximity_thresh 0.5; appearance_thresh 0.8; with_reid False; model auto — [raw botsort.yaml](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/trackers/botsort.yaml). **[primary, read]**
- `bytetrack.yaml`: same shared parameters and defaults, tracker_type bytetrack, no GMC/ReID keys — [raw bytetrack.yaml](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/trackers/bytetrack.yaml). **[primary, read]**
- Threshold semantics (docs): detections ≥ track_high_thresh enter first association; detections between low and high can recover existing tracks but cannot start new ones; detections ≤ track_low_thresh are ignored; `track()` also accepts predict args such as `conf` and `iou` — [docs/en/modes/track.md](https://raw.githubusercontent.com/ultralytics/ultralytics/main/docs/en/modes/track.md). **[primary, read]**
- Docs guidance: ByteTrack = linear Kalman + two-stage IoU matching, no ReID, no camera-motion compensation → "suits static or near-static cameras"; "for noisy detectors lower track_low_thresh; for ID flicker raise track_buffer"; BoT-SORT = ByteTrack + CMC + optional ReID → "suits handheld, drone or moving-camera footage"; static camera → gmc_method none; heavy motion → keep sparseOptFlow (ecc more accurate but slower); look-alike crowds → enable ReID and raise appearance_thresh to ≈0.85+ — [track.md](https://raw.githubusercontent.com/ultralytics/ultralytics/main/docs/en/modes/track.md). **[primary, read]**
- Code flow (byte_tracker.py): second association uses IoU only with threshold 0.5; unconfirmed tracks matched to leftover high-score detections at 0.7; unmatched unconfirmed tracks removed; new tracks only if score ≥ new_track_thresh; lost tracks removed when `frame_id - end_frame > max_frames_lost` where `self.max_frames_lost = args.track_buffer` (no frame-rate scaling); Kalman state XYAH; lost tracks have their velocity term zeroed before prediction to stop drift — [raw byte_tracker.py](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/trackers/byte_tracker.py). **[primary, read]**
- `persist`: in `on_predict_start`, if persist is true and trackers exist, they are kept; otherwise new trackers are created; in `on_predict_postprocess_end`, if persist is false and the video path changes the tracker is reset; with persist true, state carries across calls; docs: use persist only for consecutive frames of the same stream, never across unrelated images (stale state) — [raw track.py](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/trackers/track.py), [track.md](https://raw.githubusercontent.com/ultralytics/ultralytics/main/docs/en/modes/track.md). **[primary, read]**
- Results handling: if any tracked object is not yet activated the result is emptied for that frame (unconfirmed tracks hidden); IDs in `result.boxes.id`; check `result.boxes.is_track`; trackers are created at inference time, not stored in .pt — [track.py](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/trackers/track.py), [track.md](https://raw.githubusercontent.com/ultralytics/ultralytics/main/docs/en/modes/track.md). **[primary, read]**
- ReID in BoT-SORT: `model: auto` uses the YOLO detector's own features, falling back to a `-cls` model; custom .pt/.onnx/.engine/OpenVINO embedding models allowed; prebuilt ONNX ReID encoders (448 px) auto-download; ReID adds inference cost, "enable only when needed" — [track.md](https://raw.githubusercontent.com/ultralytics/ultralytics/main/docs/en/modes/track.md). **[primary, read]**
- Newer trackers: OC-SORT, Deep OC-SORT, FastTracker, TrackTrack available (ultralytics ≥ 8.4.63); TrackTrack is the default when no `tracker` is passed; TrackTrack's "Track-Aware Initialization" and FastTracker's init-IoU suppression suppress duplicate track spawns near active tracks — [track.md](https://raw.githubusercontent.com/ultralytics/ultralytics/main/docs/en/modes/track.md). **[primary, read]**
- Known limitations (docs): ReID train/val/predict not yet supported (tracking only, ONNX encoders only); persisting across unrelated streams carries stale state; tracker parameters are global, not per class/ID — [track.md](https://raw.githubusercontent.com/ultralytics/ultralytics/main/docs/en/modes/track.md), [discussion #2687](https://github.com/orgs/ultralytics/discussions/2687). **[primary, read / secondary]**

### Inferences
- Because `track_buffer` is a raw frame count, on a Pi running at ~6 FPS the default 30 frames ≈ 5 s of occlusion tolerance (vs 1 s at 30 FPS). For a robot moving at 0.2–0.3 m/s this means a lost fruit stays "alive" over ~1–1.5 m of travel, so re-activation of a wrong fruit is plausible; the buffer should be chosen in metres of travel (speed × fps), not copied from defaults.
- `match_thresh 0.8` is an IoU-distance threshold (1−IoU ≤ 0.8 ⇒ IoU ≥ 0.2); with low fps and camera motion, small fruit may not overlap at all between frames, so either raise fps, use BoT-SORT GMC, or inject odometry-based displacement before matching.

- Could not fetch docs.ultralytics.com directly (blocked); the docs content above is from the GitHub source of the same page, which may be a development version (it mentions YOLO26/YOLO27).

## KQ6. How papers handle a fruit disappearing behind a leaf and reappearing (track buffer vs frame rate, re-ID, resulting count error)

### Takeaway
Papers rarely tune track_buffer explicitly; instead they (1) count via a counting zone/line so a re-appearing fruit with a new ID is only double counted if it re-crosses the zone, (2) discard short tracks (min 5 detections; or age ≥ 1/3 of expected visibility), (3) use motion/odometry/3D to re-associate (OrangeSort, trunk tracking, IMU inter-frame prediction, SfM), and (4) modify Kalman handling of long occlusions (Huai's observation-centre recovery; AD-YOLO/MR-SORT −35.6 % IDs). Appearance ReID is rarely the chosen remedy for fruit.

### Cited Findings
- Ultralytics docs: "for ID flicker, raise track_buffer"; track_buffer comment: "higher handles occlusion, increases ID switches risk" — [track.md](https://raw.githubusercontent.com/ultralytics/ultralytics/main/docs/en/modes/track.md), [botsort.yaml](https://raw.githubusercontent.com/ultralytics/ultralytics/main/ultralytics/cfg/trackers/botsort.yaml). **[primary, read]**
- Matos CVPRW 2024: for shaky footage SORT-type settings max_age = 30, min_hits = 1 outperformed defaults; tracks with < 5 detections discarded as false detections; SfM-based 3D object set + bipartite matching to re-associate detections after intermittent occlusion and at low frame rates — [CVF PDF](https://openaccess.thecvf.com/content/CVPR2024W/Vision4Ag/papers/Matos_Tracking_and_Counting_Apples_in_Orchards_Under_Intermittent_Occlusions_and_CVPRW_2024_paper.pdf). **[secondary]**
- Liu 2018: age threshold = 1/3 of frames of camera-fruit overlap to balance FP/FN tracks; 3D localisation + size to remove double-counted tracks; orange mean error 17.1 % → −0.2 % — [arXiv](https://arxiv.org/pdf/1804.00307). **[secondary]**
- OrangeSort (citrus): motion-displacement estimation + tracking-region counting "to reduce double-counting of occluded fruit"; MAE 0.081 — [PMC9113225](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC9113225/). **[abstract]**
- Tomato robot (Zheng 2025): IMU-derived odometry predicts fruit positions between frames to keep identities through brief occlusions; MOTA 0.954 vs DeepSORT with high FP/IDSW — [MDPI DOI](https://doi.org/10.3390/agronomy15051135). **[abstract/secondary]**
- Strawberry BF-LQE-YOLOv11 + BoT-SORT: Observation Center Recovery + Observation Re-Update against Kalman drift in long occlusions; virtual counting zone for trajectory-level deduplication; counting accuracy 97.84 % — [SSRN](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=7565041). **[abstract]**
- Apple MR-SORT (BoT-SORT-based): −297 ID switches (−35.6 %), MOTA 85.6 %, R² 0.98 — [MDPI DOI](https://doi.org/10.3390/s24217012). **[abstract]**
- UAV GMC-DeepSORT: global motion compensation + dual-criteria association, IDs −22.2 %, counting accuracy 85.6 → 93.5 % — [MDPI](https://www.mdpi.com/2077-0472/16/19/2109). **[abstract]**
- Grape SORT+: Mahalanobis + IoU + Euclidean matching cascade, −62 % ID switches, counting accuracy 33 → 96 % — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0168169926001249). **[abstract]**
- Tomato clusters: "specific tracking region counting method to overcome ... ID shift"; grape: counting line "to reduce errors caused by ID switching" — [ScienceDirect tomato](https://www.sciencedirect.com/science/article/abs/pii/S0168169923001291), [ScienceDirect grape](https://www.sciencedirect.com/science/article/abs/pii/S0168169923000509). **[abstract]**
- Blueberry: "severe occlusion still causes missed detections and counting errors", 72.49 % mean accuracy "still below human precision" — [PMC12695768](https://pmc.ncbi.nlm.nih.gov/articles/PMC12695768). **[secondary]**
- 2026 edge study: low total error can hide compensating FP/FN events; dense look-alike fruit association is the main error — [arXiv 2609.13551](https://arxiv.org/pdf/2609.13551). **[secondary]**

### Inferences
- With a counting zone in the frame centre and unidirectional robot motion, a fruit that disappears behind a leaf before the zone and reappears after it with a new ID is either counted once (if it never crossed inside the zone) or missed, but not double counted; the main double-count risk is a fruit occluded while inside the zone, re-appearing still inside the zone with a new ID. Making the zone narrow and the track_buffer ≈ expected occlusion duration in frames (at the robot's fps) limits both.
- For strawberries, which are small and look alike, appearance ReID (DeepSORT/StrongSORT/BoT-SORT with_reid) has weak support; motion + odometry is the evidence-backed route.

### Gaps
- No paper found that reports count error as a function of track_buffer or of occlusion duration for any fruit.
- No strawberry-specific ID-switch counts available.

## KQ7. Effect of camera speed / fps / resolution on tracking counts in field robots

### Takeaway
Reported field speeds for counting robots are slow (0.1–0.3 m/s greenhouse; UAV/orchard higher) and low fps is common (5 fps tomato robot; 2–5 fps CPU apple pipelines); one 2026 greenhouse study found counting is "strongly affected by robot speed" with 90.1 % of ground-truth fruit recovered and count-level F1 0.898 at 0.2 m/s, slow motion even beating static images thanks to multi-view redundancy; distance (225 cm best for apple) and scanning both sides matter more than camera brand.

### Cited Findings
- 2026 greenhouse study (from search summary; title not captured): counting performance "strongly affected by robot speed"; at 0.2 m/s the system recovered 90.1 % of ground-truth count, count-level F1 0.898, and the 0.2 m/s condition outperformed static images because slow camera motion gave temporal redundancy and multiple views — [search result cited the "Development of a plant sensing robot using virtual space" / edge-hardware cluster; the exact URL for this figure is uncertain](https://www.sciencedirect.com/science/article/pii/S2772375526006544). **[secondary; attribution uncertain, verify]**
- Ren et al. 2023 strawberry platform: 0.3 m/s travel; keyframe interval modelled from fps, speed, intrinsics, fruit distance; stable for fps > 15 and v = 0.2–0.4 m/s — [PMC10167025](https://pmc.ncbi.nlm.nih.gov/articles/PMC10167025/). **[secondary]**
- Tomato greenhouse study: constant speed 0.1 m/s and 5 fps capture "to minimize motion blur" — [search summary; one of the tomato robot papers, e.g. Agronomy 2025](https://doi.org/10.3390/agronomy15051135). **[secondary; attribution uncertain]**
- Apple scanning conditions (Felip-Pomés 2026): best MAPE 6.91 %, R² 0.733 with ZED 2 at 225 cm near harvest; longer distance improved counts; Kinect more consistent across dates; both sides needed — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0168169926009282). **[abstract]**
- Matos CVPRW 2024 is explicitly about low frame rates + unconstrained camera motion (SfM association) — [CVF](https://openaccess.thecvf.com/content/CVPR2024W/Vision4Ag/papers/Matos_Tracking_and_Counting_Apples_in_Orchards_Under_Intermittent_Occlusions_and_CVPRW_2024_paper.pdf). **[secondary]**
- CPU pipelines in the literature run at 2–5 fps (Gao trunk tracking) and 3–5 fps (twice-matched), with counting accuracy 91.49 % and R² 0.93 respectively — [ScienceDirect Gao](https://www.sciencedirect.com/science/article/abs/pii/S0168169922003179), [ScienceDirect twice-matched](https://www.sciencedirect.com/science/article/abs/pii/S1537511023001885). **[abstract]**
- Pi 5 CPU detection ≈7–8 FPS for nano models at 640 px (ONNX/NCNN) — [Ultralytics RPi guide](https://docs.ultralytics.com/guides/raspberry-pi), [EJ Tech](https://www.ejtech.io/learn/yolo-on-raspberry-pi). **[secondary]**
- Karki 2025 strawberry used 1920×1080 frames with a centre vertical ROI — [MDPI DOI](https://doi.org/10.3390/agriculture15181906). **[secondary]**

### Inferences
- A Pi-5 robot at ~6 FPS and 0.2 m/s moves ≈3.3 cm per frame; at a typical 40–60 cm strawberry-bed working distance with a ~70° HFOV camera, that is a few percent of frame width per frame, which keeps IoU-based matching feasible for fruit ≥ ~20 px; at 0.5 m/s or with 320 px input it would not. Speed should therefore be set from fps × desired per-frame displacement, mirroring Ren et al.'s keyframe-spacing model.
- The literature's success with 2–5 fps CPU pipelines (apple) suggests low fps is survivable if the association uses known camera motion (odometry/trunk displacement), reinforcing the GMC/odometry recommendation.

### Gaps
- No study provides a count-error vs speed vs fps curve for strawberries; the 0.2 m/s / 90.1 % figure comes from a search summary whose exact source could not be confirmed.
- No study found on the effect of input resolution (e.g. 320 vs 640) on tracking counts in fruit.
